# Baseline MVP Architecture

## Scope

This specification supports the baseline video content factory: catalog
management for applications and companies, content-project management with
optional catalog associations, and one stored user-authored script or prompt
draft per project. It does not include authentication, AI integrations,
background jobs, agentic workflows, or visual/video asset creation.

## Runtime and Project Structure

The application is a single FastAPI process served by the Stage 4 `run.sh`
script at `http://127.0.0.1:8000`. It uses the pinned FastAPI and Uvicorn
dependencies, Python's standard-library `sqlite3`, and Bootstrap loaded by
the browser without a Node build step.

```text
backend/
  main.py                 FastAPI application, routes, static-file mounting
  database.py             connection lifecycle, schema initialization, seed setup
  schemas.py              request and response validation models
  repositories.py         SQL operations and persistence mapping
  data/
    vid_factory.db        local SQLite database (gitignored; created at runtime)
frontend/
  index.html              application shell and Bootstrap markup
  app.js                  API client, rendering, event handling, UI state
  styles.css              small application-specific styling
docs/
  architecture.md         this specification
```

`backend/main.py` owns HTTP concerns: route registration, validation error
translation, and serving the frontend. `backend/schemas.py` owns the public
request/response shapes. `backend/repositories.py` owns all SQL statements and
returns persistence records. `backend/database.py` owns database connections,
foreign-key enforcement, idempotent schema creation, and idempotent seed
creation. The frontend never opens SQLite or constructs SQL.

## Database Design

The database is one local SQLite file at `backend/data/vid_factory.db`.
Connections enable `PRAGMA foreign_keys = ON`. Schema setup runs before the
application begins serving requests and is safe to repeat. Timestamps use UTC
ISO-8601 text values generated by the backend.

```sql
CREATE TABLE applications (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE CHECK (length(trim(name)) > 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE companies (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE CHECK (length(trim(name)) > 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE content_projects (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL CHECK (length(trim(title)) > 0),
  description TEXT NOT NULL DEFAULT '',
  application_id INTEGER REFERENCES applications(id) ON DELETE SET NULL,
  company_id INTEGER REFERENCES companies(id) ON DELETE SET NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE drafts (
  id INTEGER PRIMARY KEY,
  content_project_id INTEGER NOT NULL UNIQUE
    REFERENCES content_projects(id) ON DELETE CASCADE,
  draft_type TEXT NOT NULL CHECK (draft_type IN ('script', 'prompt')),
  body TEXT NOT NULL CHECK (length(trim(body)) > 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX idx_content_projects_application_id
  ON content_projects(application_id);
CREATE INDEX idx_content_projects_company_id
  ON content_projects(company_id);
```

Names and project titles are trimmed before persistence. Duplicate catalog
names are rejected. `description` may be empty. An omitted association is
stored as `NULL`; deleting an application or company sets its project
references to `NULL`, preserving the project and its draft. A draft cannot
exist without a project and is deleted with that project.

On a new database, Stage 6 supplies a small, deterministic set of application
and company names in `database.py`. Seed insertion must use conflict-safe,
idempotent inserts, so starting the app again never duplicates or overwrites
user changes. Exact seed names are an implementation choice, not an API
contract.

## API Conventions

All endpoints are JSON APIs under `/api`. Successful create operations return
`201`; successful reads, updates, and deletes return `200`. Deletion returns
the deleted resource. Missing resources return `404`. Invalid payloads,
including blank required strings, invalid draft types, duplicate names, or an
unknown association ID, return `422` with a JSON error detail. Unexpected
server errors return `500` and must not expose SQL internals.

Responses use integers for IDs and camel_case JSON field names. Timestamp
fields are included in detail and list records for consistency.

### Shared Resource Shapes

```json
{
  "id": 1,
  "name": "Example application",
  "created_at": "2026-09-08T12:00:00Z",
  "updated_at": "2026-09-08T12:00:00Z"
}
```

Applications and companies use this catalog shape. Their create and update
payload is `{ "name": "..." }`.

Project requests use:

```json
{
  "title": "Launch idea",
  "description": "Optional context",
  "application_id": 1,
  "company_id": 2
}
```

`description`, `application_id`, and `company_id` are optional on create;
clients send `null` to clear either association on update. The project response
includes IDs plus resolved catalog names for display:

```json
{
  "id": 1,
  "title": "Launch idea",
  "description": "Optional context",
  "application_id": 1,
  "application_name": "Example application",
  "company_id": 2,
  "company_name": "Example company",
  "created_at": "2026-09-08T12:00:00Z",
  "updated_at": "2026-09-08T12:00:00Z"
}
```

Draft requests and responses use `draft_type` (`script` or `prompt`) and
`body`. A project detail response includes `draft`, which is either a draft
object or `null`.

```json
{
  "id": 1,
  "content_project_id": 1,
  "draft_type": "script",
  "body": "User-authored draft text",
  "created_at": "2026-09-08T12:00:00Z",
  "updated_at": "2026-09-08T12:00:00Z"
}
```

### Routes

| Method | Route | Request body | Success response |
| --- | --- | --- | --- |
| GET | `/api/applications` | — | `200` array of applications, ordered by name then ID |
| POST | `/api/applications` | catalog create payload | `201` application |
| GET | `/api/applications/{id}` | — | `200` application |
| PUT | `/api/applications/{id}` | catalog update payload | `200` application |
| DELETE | `/api/applications/{id}` | — | `200` deleted application |
| GET | `/api/companies` | — | `200` array of companies, ordered by name then ID |
| POST | `/api/companies` | catalog create payload | `201` company |
| GET | `/api/companies/{id}` | — | `200` company |
| PUT | `/api/companies/{id}` | catalog update payload | `200` company |
| DELETE | `/api/companies/{id}` | — | `200` deleted company |
| GET | `/api/projects` | — | `200` array of project display records, ordered by updated_at descending then ID descending |
| POST | `/api/projects` | project payload | `201` project detail, with `draft: null` |
| GET | `/api/projects/{id}` | — | `200` project detail including `draft` |
| PUT | `/api/projects/{id}` | complete project payload | `200` project detail including current `draft` |
| DELETE | `/api/projects/{id}` | — | `200` deleted project |
| PUT | `/api/projects/{id}/draft` | draft type (`script` or `prompt`) and body | `200` created or updated draft |

`PUT /api/projects/{id}/draft` is an upsert: it creates the sole draft when
none exists and updates that same record otherwise. It returns `404` when the
project is missing. Project creation/update validates that each non-null
association ID exists.

## Frontend Responsibilities and State Flow

The frontend is a single Bootstrap-based browser interface served by FastAPI.
It provides three navigable views: Applications, Companies, and Content
Projects. Each catalog view lists records and exposes create, detail, edit,
and delete controls. The project view lists projects, opens a project detail
form, and supplies application/company selectors populated from the catalog
API. The project detail view displays its draft state and provides one form to
save or edit the script/prompt draft.

`app.js` owns browser-only state: the active view, currently selected resource,
loaded catalog options, displayed list/detail data, form values, and
success/error notices. It calls the API with `fetch`; it does not duplicate
business validation or persist data locally. After every successful mutation,
it refetches the relevant list or detail so the UI reflects persisted state.
On a failed request it preserves form input and renders the API error message.

```text
Browser action
  -> frontend validates obvious required fields and calls /api
  -> FastAPI validates payload and delegates to repository
  -> repository reads/writes SQLite in a transaction
  -> FastAPI serializes JSON response
  -> frontend refreshes affected view and shows success or error feedback
```

## Backend Responsibilities

The backend owns request validation, normalization, referential-integrity
checks, schema and seed initialization, SQL transactions, API error mapping,
and static frontend delivery. It must not generate content, contact AI or
media services, or require a separate database server. Stage 6 implements this
contract without changing the Stage 4 environment.
